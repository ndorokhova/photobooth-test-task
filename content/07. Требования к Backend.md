# Требования к Backend

## 1. Целевая схема

В обработке заявки на отправку фотографии по электронной почте участвуют:
- приложение фотокиоска;
- Backend API;
- Database;
- Object Storage;
- сервис отправки электронной почты;
- внешний Email Provider.

До отправки в Backend API фотография хранится локально в приложении фотокиоска. При выборе отправки на электронную почту приложение фотокиоска передаёт файл в Backend API вместе с параметрами запроса.

Backend API и сервис отправки электронной почты используют общую Database. Database хранит заявки и служит источником заданий для асинхронной обработки.

Файл фотографии хранится в Object Storage. Database содержит только метаданные фотографии и ссылку на неё. Сервис отправки электронной почты получает файл из Object Storage по данным заявки.

## 2. Целевой процесс

1. Приложение фотокиоска передаёт Backend API:

    - sessionId;
    - файл фотографии;
    - адрес электронной почты;
    - personalDataConsentAccepted — признак согласия на обработку персональных данных.

2. Backend API проверяет параметры запроса.
3. Backend API ищет в Database запись по sessionId; если она отсутствует, создаёт новую запись.
4. Backend API присваивает фотографии photoId и сохраняет файл в Object Storage.
5. Backend API сохраняет метаданные фотографии в Database.
6. Backend API создаёт requestId и сохраняет в Database заявку на отправку со статусом PENDING.
7. После сохранения заявки Backend API возвращает приложению фотокиоска подтверждение принятия заявки — 202 Accepted.
8. Сервис отправки электронной почты каждые 15 секунд выбирает из Database заявки со статусом PENDING, готовые к обработке.
9. Сервис получает фотографию из Object Storage и формирует письмо.
10. Сервис передаёт письмо Email Provider.
11. Email Provider возвращает сервису подтверждение принятия письма.
12. После принятия письма Email Provider сервис обновляет в Database статус заявки на SENT.
13. При временной ошибке сервис сохраняет в Database сведения о попытке и повторяет обращение к Email Provider.
14. После исчерпания повторных попыток сервис обновляет в Database статус заявки на FAILED.

!!! note "Ограничение тестового задания"
    В рамках тестового задания не детализируются сценарии ошибок и восстановления при недоступности внутренних компонентов системы, включая Database и Object Storage. Описываются ошибки валидации запроса, повторные обращения к Email Provider и результат обработки заявки.

## 4. Обоснование асинхронной обработки

Асинхронная обработка выбрана по следующим причинам:
- пользователь не ожидает ответа Email Provider у фотокиоска;
- временная недоступность Email Provider не мешает Backend API принять от приложения фотокиоска заявку на отправку фотографии;
- система может выполнять повторные попытки без участия пользователя;
- завершение пользовательской сессии не отменяет уже принятую заявку.

## 5. Статусы заявки

| Статус | Описание |
|---|---|
| PENDING | Заявка ожидает первой или повторной попытки отправки. |
| PROCESSING | Сервис отправки электронной почты принял заявку в обработку и выполняет отправку письма. |
| SENT | Email Provider принял письмо от сервиса отправки электронной почты для дальнейшей доставки получателю. |
| FAILED | Сервис отправки электронной почты не смог передать письмо Email Provider после выполнения предусмотренных повторных попыток. |

Ошибки до возврата 202 Accepted не относятся к статусу FAILED: в этом случае заявка не считается принятой.

## 6. Функциональные требования

### 6.1. Приём и проверка запроса от приложения фотокиоска
- **BE-01.** Backend API должен принимать от приложения фотокиоска запрос на отправку фотографии.
- **BE-02.** Backend API должен проверять наличие обязательных параметров: sessionId, email, personalDataConsentAccepted и файла photo.
- **BE-03.** Backend API должен проверять формат электронной почты и значение personalDataConsentAccepted = true.
- **BE-04.** Backend API должен искать в Database запись, связанную с переданным sessionId. Если запись отсутствует, Backend API должен создать её. Отсутствие записи не является ошибкой.
- **BE-05.** Backend API не должен создавать новую заявку, если для текущей пользовательской сессии уже существует принятая заявка на отправку фотографии по электронной почте.
- **BE-06.** При повторном запросе с теми же sessionId, фотографией и email Backend API должен вернуть приложению фотокиоска requestId и status существующей заявки.
- **BE-07.** Если для пользовательской сессии уже существует принятая заявка, а повторный запрос содержит другую фотографию или другой адрес электронной почты, Backend API должен отклонить повторный запрос.

### 6.2. Сохранение фотографии и создание заявки
- **BE-08.** Backend API должен присваивать фотографии уникальный photoId.
- **BE-09.** Backend API должен сохранять фотографию в Object Storage.
- **BE-10.** Backend API должен сохранять в Database метаданные фотографии и связь с пользовательской сессией.
- **BE-11.** Backend API должен сформировать уникальный requestId и сохранить в Database заявку, содержащую requestId, sessionId, photoId, адрес электронной почты и статус PENDING.
- **BE-12.** Backend API должен возвращать приложению фотокиоска 202 Accepted только после успешного сохранения фотографии в Object Storage и создания в Database заявки со статусом PENDING.
- **BE-13.** Бинарное содержимое фотографии не должно сохраняться в Database.

### 6.3. Асинхронная обработка и передача письма Email Provider
- **BE-14.** Сервис отправки электронной почты должен каждые 15 секунд выбирать из Database готовые к обработке заявки со статусом PENDING и атомарно переводить их в статус PROCESSING.
- **BE-15.** Сервис отправки электронной почты должен получать фотографию из Object Storage.
- **BE-16.** Сервис отправки электронной почты должен формировать письмо и передавать его Email Provider.
- **BE-17.** Сервис отправки электронной почты должен прикладывать к письму выбранную фотографию в формате JPEG.
- **BE-18.** После получения подтверждения от Email Provider сервис отправки электронной почты должен обновлять в Database статус заявки на SENT.

### 6.4. Обработка ошибок и повторные попытки
- **BE-19.** При временной технической ошибке сервис отправки электронной почты должен сохранять сведения о попытке. Если повторные попытки не исчерпаны, сервис должен возвращать заявке статус PENDING и планировать следующую попытку в соответствии с [[#retry-attempts|разделом 7 «Повторные попытки»]].
- **BE-20.** После исчерпания повторных попыток сервис отправки электронной почты должен обновлять в Database статус заявки на FAILED.
- **BE-21.** Для заявки в Database должны сохраняться количество попыток и код последней ошибки.

### 6.5. Завершение сессии и повторный запрос
- **BE-22.** Завершение пользовательской сессии не должно отменять обработку принятой заявки.
- **BE-23.** При повторном запросе после истечения времени ожидания Backend API не должен создавать новую заявку, если первоначальная заявка уже была принята.

## 7. Повторные попытки {#retry-attempts}

| Попытка | Время выполнения |
|---|---|
| Первая попытка | При первом выборе заявки сервисом |
| Повторная попытка 1 | Через 1 минуту после неуспешной попытки |
| Повторная попытка 2 | Через 5 минут после неуспешной попытки |

Время ожидания ответа Email Provider для одной попытки отправки не должно превышать 10 секунд. Если ответ не получен за это время, попытка считается неуспешной по тайм-ауту.

Повторные попытки выполняются при:
- превышении времени ожидания ответа Email Provider;
- сетевой ошибке;
- HTTP 429;
- HTTP 5xx.

После трёх неуспешных обращений к Email Provider сервис отправки электронной почты обновляет в Database статус заявки на FAILED.

## 8. API

### `POST /api/v1/email-requests`

**Назначение** — создаёт заявку на отправку фотографии на электронную почту.

**Content-Type:** multipart/form-data

### Параметры тела запроса

| Параметр | Тип | Обязательный | Описание |
|---|---|---:|---|
| sessionId | String (UUID) | Да | Технический идентификатор пользовательской сессии, создаваемой в клиентском приложении фотокиоска при начале взаимодействия. Должен быть уникальным в рамках системы и может отличаться от номера сессии, отображаемого в интерфейсе фотокиоска. |
| email | String | Да | Адрес получателя |
| personalDataConsentAccepted | Boolean | Да | Признак согласия на обработку персональных данных |
| photo | File | Да | Одна выбранная фотография в формате JPEG |

### Ответ 202 Accepted

!!! info "Значение 202 Accepted"
    Ответ 202 Accepted означает, что фотография сохранена, а заявка принята к асинхронной обработке. Ответ не означает фактическую доставку письма пользователю.

202 Accepted

```json
{
  "requestId": "5bdf64d5-9e50-45f3-93fc-97a81c3ea943",
  "status": "PENDING"
}
```

После получения 202 Accepted приложение фотокиоска отображает [[06. Требования к интерфейсам#screen-5|экран 5 в состоянии 5.1 «Запрос принят»]].

### Возможные ошибки

| HTTP | Описание |
|---|---|
| 400 Bad Request | Отсутствуют обязательные параметры либо данные некорректны |
| 409 Conflict | Параметры повторного запроса конфликтуют с принятой заявкой |
| 500 Internal Server Error | Внутренняя ошибка системы |
| 503 Service Unavailable | Система временно не может принять заявку |
### Время ожидания ответа

Приложение фотокиоска должно ожидать ответ Backend API не более 15 секунд.
Если ответ не получен за это время, запрос считается неподтверждённым со стороны приложения. Повторный запрос не должен создавать новую заявку, если первоначальная заявка уже была принята Backend API.

## 9. Примерная структура Database

Ниже приведена примерная логическая структура Database для сценария отправки фотографии. Она хранит данные о пользовательской сессии, фотографии, заявке на отправку и результатах обращений к Email Provider. Файл фотографии хранится в Object Storage, а в Database сохраняется только ссылка на него и связанные метаданные.

В рамках тестового задания приводится только примерная структура таблиц и их основных полей. Подробное описание полей Database, их типов, ограничений и правил валидации не рассматривается.

| Таблица             | Назначение                                                                        | Основные поля                                                                                                                 |
| ------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| sessions            | Хранит записи о сессиях фотокиоска, впервые обратившихся в Backend API.            | session_id, created_at                                                                                                       |

## 10. Дополнительные требования

- Обмен между приложением фотокиоска и Backend API должен выполняться по защищённому соединению.
- Адрес электронной почты и фотография не должны записываться в технические логи.
- Должен выполняться мониторинг количества заявок в статусах PENDING, PROCESSING и FAILED.
- Адрес электронной почты, копия фотографии на сервере и иные персональные данные должны быть удалены после завершения обработки заявки, но не позднее 24 часов с момента её принятия. Обезличенные данные о ходе и результате отправки могут храниться для статистики и анализа.
